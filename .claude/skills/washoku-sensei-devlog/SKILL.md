# Washoku Sensei（CDA版）学習・開発記録

Washoku Sensei は、DWWM の課題として作った Symfony / Doctrine / MySQL / Twig / Tailwind CSS / Docker の Web アプリ。これを **CDA（Concepteur Développeur d'Applications, RNCP37873）の課題として作り替えている**。

## 道具の役割分担

- **ChatGPT**：CDA の授業内容を日本語で説明し、理解度を確認する。結果を「授業メモ」の形で出す。
- **Claude（Web 版）**：設計の相談、試験の書類（dossier de projet など）の作成。
- **Claude Code**：リポジトリを実際に確認し、授業の内容がコードに入っているかを確かめ、記録を書く。
- **ユーザー**：設計を決め、コードを書くか承認し、理解度を確認し、記録の更新を承認する。

どの道具も、ほかの道具の会話を自動では読めない。ChatGPT の授業メモは、ユーザーが貼り付けるか `docs/learning/inbox/` に置いたときだけ材料になる。

## 守るルール

1. **ユーザーの承認なしにファイルを書かない**。書く内容を先に見せて、「OK」をもらってから保存する。
2. **このスキルではアプリのコードを変更しない**。書くのは `docs/` の中だけ。
3. **理解の段階を区別する**：授業で学んだ／理論として理解した／まだ不明／プロジェクトで使った。「プロジェクトで使った」は、リポジトリの中に証拠（ファイル名・行）があるときだけ書く。
4. **設計判断の出どころを区別する**：ユーザーが決めたこと、AI（Claude または ChatGPT）が提案してユーザーが採用したこと、まだ検討中のこと。
5. **わからない情報を推測で埋めない**。まとめて1回だけ質問する。ユーザーが言っていないこと（作業時間、完成度など）は書かない。
6. **秘密情報を記録しない**：`.env` の中身、パスワード、OAuth の秘密鍵、個人データ。

## ファイル構成

```
docs/
├── PROJECT_CONTEXT.md     # プロジェクト全体の引き継ぎ資料（週ごとに更新）
├── cda-competences.md     # CDA の能力ごとの証拠の一覧（週ごとに更新）
├── dwwm-to-cda.md         # DWWM 版からの作り替えの記録
├── open-issues.md         # 未解決の問題の一覧
├── learning/
│   ├── inbox/             # ChatGPT の授業メモを置く場所（処理したら learning/ に移す）
│   └── YYYY-MM-DD-トピック.md   # 学習記録
├── devlog/
│   └── YYYY-MM-DD.md      # 日々の開発記録
├── weekly/
│   └── YYYY-Www.md        # 週のまとめ（例：2026-W48.md）
└── decisions/
    └── NNN-タイトル.md     # 設計判断の記録（ADR）
```

ファイルやフォルダがなければ、承認をもらってから作る。`PROJECT_CONTEXT.md` と `dwwm-to-cda.md` を初めて作るときは、composer.json、compose.yaml、src/、templates/、migrations/、README、既存の文書を読んで下書きする。

## モードの判断

- ChatGPT の授業メモが貼られた／inbox にある、「授業の内容を記録して」 → **学習モード**
- 「今日の記録」「開発記録をつけて」 → **日次モード**（その日に学習メモがあれば、学習モードを先に行う）
- 「週のまとめ」「全体を更新して」、または前回の週次更新から7日以上たっている → **週次モード**（提案して、承認されたら行う）
- 「設計判断を記録して」、または作業中に設計上の選択があった → **設計判断の記録**

## 1. 材料を集める（共通）

リポジトリにアクセスできる場合は、自分でコマンドを実行する。できない場合は、ユーザーに出力を貼ってもらう。

```bash
git log --since="today 00:00" --stat --oneline
git status --short
git diff --stat HEAD
ls docs/learning/inbox/ 2>/dev/null
```

## 2. 学習モード

### 2-1. 授業メモを読む

ChatGPT の授業メモは、次の形で来ることを想定する（形が違っても、読み取れる範囲で使う）。

```markdown
# 授業メモ YYYY-MM-DD：トピック
## 授業で扱った内容
## 自分の言葉での説明
## 理解の段階
- 理論として理解した：
- まだ不明：
## Washoku Sensei に使えそうな点
## Claude Code に確認してほしいこと
```

### 2-2. コードと照らし合わせる

「Washoku Sensei に使えそうな点」と「Claude Code に確認してほしいこと」について、リポジトリの中を検索し、その考え方がすでにコードにあるかを調べる。見つかった場合はファイル名と行を、見つからない場合は「未実装」と書く。どう実装するかは提案にとどめ、コードは変更しない。

### 2-3. `docs/learning/YYYY-MM-DD-トピック.md` を書く（承認後）

```markdown
# 学習記録 YYYY-MM-DD：トピック
- 出典：CDA の授業（ChatGPT で整理）
- 関連する CDA の能力：CPn

## 要点
## 理解の段階
| 項目 | 授業で学んだ | 理論として理解 | まだ不明 | プロジェクトで使った（証拠） |
|---|---|---|---|---|
| | ✓ | ✓ | | src/... L.xx |

## Washoku Sensei との関係
- すでにあるもの：
- これから取り入れられそうなもの（提案）：

## 次に確認すること
```

「まだ不明」の項目は、ChatGPT に持っていく質問として最後に一覧にする。処理した inbox のファイルは、承認をもらってから削除するか、`learning/` 内の記録にまとめる。

「次回の作業」は、次の会話でこれだけ読めば再開できるくらい具体的に書く。悪い例：「検索機能を続ける」。良い例：「`RecipeRepository::findByIngredients()` の JOIN を直して、`tests/RecipeSearchTest.php` を通す」。

### `docs/open-issues.md`

```markdown
| ID | 内容 | 見つけた日 | 影響範囲 | 状態 | メモ |
|---|---|---|---|---|---|
| OI-001 | | | | 調査中 | |
```

解決したものは状態を「解決済み（YYYY-MM-DD）」にして、週次モードのときに「解決済み」セクションへ移す。

## 4. 設計判断の記録（ADR）

アーキテクチャ（レイヤー構成、API 化など）、ライブラリの選択、DB 構造（SQL と NoSQL の使い分けを含む）、認証方式、セキュリティ、テスト方針、デプロイ方法など、あとから「なぜこうしたのか」を聞かれそうな判断は `docs/decisions/NNN-タイトル.md` に残す。

```markdown
# NNN. タイトル
- 日付：YYYY-MM-DD
- 状態：採用 / 検討中 / 置き換え済み（→ NNN）
- 判断した人：ユーザー / AI の提案をユーザーが採用（どの AI か）
- DWWM 版との関係：新規 / DWWM 版の〇〇を変更
- 関連する授業：learning/...（あれば）

## 背景
## 検討した選択肢（長所／短所）
## 決定
## 理由（ユーザーが述べた理由をそのまま書く）
## 影響
## CDA の能力との対応
```

## 5. 週次モード

1. **`docs/weekly/YYYY-Www.md`**：その週の devlog と学習記録を読んで、完成したこと、学んだこと、主な設計判断、解決した問題と残っている問題、証拠が増えた CDA の能力、来週の目標（3つまで）をまとめる。
2. **`docs/cda-competences.md`**：能力ごとの証拠を更新する。証拠がないものは「未着手」と書き、実際にないものを証拠として書かない。能力の名前と番号は、ENLEARN の資料が手元にあればそれに合わせる。

   ```markdown
   ## 1. 安全なアプリケーションを開発する
   | 能力 | 証拠 | 状態 |
   |---|---|---|
   | CP1 開発環境の導入と設定 | | |
   | CP2 ユーザーインターフェースの開発 | | |
   | CP3 業務コンポーネントの開発 | | |
   | CP4 プロジェクト管理への参加 | | |
   ## 2. レイヤー構造の安全なアプリケーションを設計・開発する
   | CP5 要件分析とモックアップ | | |
   | CP6 ソフトウェアアーキテクチャの定義 | | |
   | CP7 リレーショナル DB の設計と構築 | | |
   | CP8 SQL／NoSQL のデータアクセスコンポーネント | | |
   ## 3. 安全なアプリケーションのデプロイを準備する
   | CP9 テスト計画の準備と実施 | | |
   | CP10 デプロイの準備と文書化 | | |
   | CP11 DevOps によるリリースへの参加 | | |
   ```

3. **`docs/dwwm-to-cda.md`**：アーキテクチャ、データベース、テスト、デプロイ、セキュリティなどについて、DWWM 版と CDA 版の違いと、関連する設計判断を表にする。
4. **`docs/PROJECT_CONTEXT.md`**：**このファイルだけを読んだ別の AI や開発者が、作業を引き継げる資料**にする。Claude 固有の機能や過去の会話を前提にしない。章立て：概要（DWWM から CDA への作り替えであること、共同開発者 CHAOUCHI）／主な機能と進み具合／技術スタックとバージョン（composer.json と compose.yaml から）／環境構築と起動方法／ディレクトリ構成とアーキテクチャ／コーディング規約（コミットは feat:/fix:/docs: など）／主な設計判断／DWWM 版からの変更／未解決の問題／現在の状態と次のステップ／AI への作業依頼の仕方（まずこのファイル、open-issues.md、最新の devlog を読むこと。秘密情報は共有しない）。

実装されていないものを「完了」と書かない。古くなった記述は直す。

## 6. 保存とバックアップ

記録を保存したら、ユーザーに次の確認を促す（すでに終わっている項目は飛ばす）。

```bash
git status            # .env.local などの秘密情報が含まれていないか確認
git add docs/
git commit -m "docs: 学習・開発記録 YYYY-MM-DD"
git push              # 非公開のリモートリポジトリへ
```

DB のダンプは、リポジトリの外（例：`~/backups/washoku-sensei/`）に保存し、Git には入れない。
